## 2. 三段演进（每段的结论都要记住，不要重走）

### 2.1 工具层：Orca 和 Wake 不是竞品（10-28 晚）

**问题**：谁更合适组建 agent 舰队？
**结论**：不同层——**Orca = 驾驶舱（跑/编/盯），Wake = 档案室（记/查/喂历史）**，不冲突。`[原话][二手]`

| | Orca（`stablyai/orca`） | Wake（`iAmCorey/Wake`） |
|---|---|---|
| 定位 | Agent IDE / 多 agent 编排器 | 多 agent 会话浏览器（纯只读） |
| 技术栈 | TypeScript + Electron | Rust + GPUI |
| 规模（10-28 快照） | **108,684** star，2026-03 建，每天发版 | 1,493 star，2026-08 首发，v0.10.2 |
| 平台 | macOS/Windows/Linux + iOS/Android | macOS 主，Windows/Linux experimental |
| 会不会跑 agent | **会**：起进程、开 git worktree | 不会，最多复制一条命令 |
| 编排原语 | **Run / Task / Dispatch / Message / Decision gate**；任务有 spec+依赖+状态（pending/ready/dispatched/completed/failed/blocked）；worker 回报 `worker_done`+heartbeat | 无编排概念 |
| 历史 | 只管自己起的会话 | **24 家 agent** 的本地目录全索引，CJK+代码子串全文搜索，子代理挂父会话 |
| 给 agent 查历史 | Orca CLI 反向驱动 | `wake-mcp` + `wake-cli` 只读五工具：search / list_sessions / get_session / list_projects / list_memories |
| 权限默认 | ⚠️ 默认帮你填 bypass（`--dangerously-skip-permissions`、`--yolo`） | 只读，零风险 |

**当时的四个坑（对你这个场景仍然有效）**：

1. Orca 里的 DSH 是 `dsh-tui` profile 的**终端 TUI 形态**，不是现在这个桌面 GUI。
2. **DSH 不在 Orca 的受监管 worker 名单里**（名单是 ZCode / Qoder / Qwen Code / Antigravity 那几家）；想真正吃 Run/Task/DAG，主力得选 Claude Code / Codex / OpenCode，DSH 当普通 pane。
3. Orca 整套建立在 **git worktree** 上——ChatBox 这种"写文档"的非 git 讨论区用不上；舰队模型对**代码仓库**才顺。
4. 成熟度：Orca 8,088 个未关闭 issue、编排层 Experimental 默认关；Wake 单人维护、Windows 实验态。

**10-29 15:20 用户要"舰队工具怎么用才好"后的产出**（Orca 用法规则，代码场景才用）`[原话]`：
只对 git 仓库用；扇出上限 3–5 且各喂不同侧重；task spec 写死验收物；跨任务歧义用 decision gate；**别让两个 worker 碰同一批文件**（worktree 隔离文件系统，不隔离语义）；`worker_done` 带 files-modified 人工 review；别长开 worker pane；并行 token 线性涨；worktree 里不要有生产凭证/`.env`；分工上 **Orca = 代码仓库驾驶舱、DSH = 日常助理**。

**10-29 的更根本取舍**（比"哪个工具强"更值得留）：**真相存在哪**——
Orca = git worktree + 收件箱消息；Raft = 聊天室消息；DSH team task = 任务板文件。
不是"都没差别"，而是"你的裁决要落在哪种介质上"。`[原话]`

### 2.2 组织层：部门制四件套，零新工具（10-29 16:06 之后的答复 `[原话]`）

**诊断三句**（这段是整条线最结实的地方）：

1. **session 孤立不是 bug**。隔离 = 独立上下文 = 独立判断；合并成一个 session 得到的是"什么都懂一点、什么都不专业"的总管。
2. **失联才是坏事**。缺的是汇报制度，不是共享大脑。
3. **你的"计划经济委员会"本质是 ETL 系统，不是聊天系统**。中央不需要和每个部门对话，它需要部门**按时交格式化报告**；聊天是异常通道（发现矛盾才开会质询），不是主干。

**正确的组织形态 = 分立的部门 + 强制的汇报**，每部门一个**固定出口**（固定格式、固定周期、落 Obsidian 固定目录）= 民主集中制：采集分散、汇总集中。

由此得到的**部门制四件套（今天可做，零新工具）**：

| # | 件 | 内容 |
|---|---|---|
| 1 | 一个进程 | headless agent：`claude -p` / `codex exec` / DSH 定时任务 |
| 2 | 一个信息源 | MCP server 或 CLI（金融=交易所 RSS；开源=GitHub trending+issue；技术=HN/arXiv；政策=官方公告） |
| 3 | 一个作业模板 | frontmatter + 3–5 个固定小节 + 来源链接 + 置信度 + 一句"我认为的变化" |
| 4 | 一个周期 | 每天 08:00 / 每周一 |

产物：`Obsidian/00-inbox/<部门>/<日期>.md`。

**工具器官位置（别都装）**：DSH=前额叶（必需）；Obsidian=语言区（必需）；Wake=海马体（建议装）；Orca=手（改代码才用）；Raft=会议室（异常时才开）。`[原话]`

**列宁主义三搬一不搬**：

- 能搬：民主集中制（采集分散、汇总集中）；汇报制度（固定周期、固定格式、必须带原始出处）；纪律红线（不许编造、不许无源引用、越界必须上报）。
- **不能搬：先锋队"掌握真理"的认识论**。agent 不知道自己错，所以必须**保留异议**——同一件事两部门结论不一致时**不要合并**，两份原始报告进 `_disputes/`，留待下一轮或交叉部门裁。只存结论不存分歧，这套制度会稳定生产"自信的废话"。`[原话]`

**最缺的一环 = 交叉核对**：同主题派两个不同信息源的部门，结论不一致进 dispute（回声室是部门制的必发病）。

**现实性结论**：

- 现实：部门制 + MCP 源 + Obsidian inbox + 推送，今天可做，一个月跑三条线。
- 不现实：先装 Orca+Raft+Wake 再"组织起来"——会变成维护四个系统的人，而组织还没成立。
- fork 工厂在这件事上**用不上**（全是标准件：MCP 协议、Markdown、cron、headless CLI），不需要 fork 任何工具。

**建议顺序（M0–M3，当时提出、用户未回应）**：

- M0（一周）：《组织章程》一页 + `00-inbox/_template.md`
- M1（两周）：只跑一个部门（建议「开源动向」），每天 08:00 交作业，自己读一周改模板
- M2：加第二个部门 + 交叉核对（同主题双部门）+ 微信推送
- M3（可选）：出现改代码任务才上 Orca；要当面质询才上 Raft；Wake 随时装

### 2.3 形状层：四级模型与 Super-agent 对照（10-31 晚）

**用户给的四级**：中央（Router）→ 部委 → 部门（worker，有 session）→ 班组（subagent，真干活）。`[原话]`

**与 DSH 那篇文章（Super-agent 设计探索）逐条对照的结论**`[文档]`：[分析文档](../research/wechat-articles/2026-10-31-Super-agent设计探索-DSH下一代harness-要点与分析.md)

| 你的说法 | 文章/DSH 的做法 | 判断 |
|---|---|---|
| 一个 session 一个机器人 | 一 Ticket 一 Executor（Worker 隔离层） | ✅ 一致 |
| 遵守规则（orca） | Policy 版本 + Mandate + 准入表 + observe→auto | ✅ 比 Orca 更严 |
| 每个人都可以通话（raft） | 用**同一个 Thread 多订阅者**替代 agent 间直接通信 | ⚠️ **方向相反**（A2A vs 共享线程） |
| （缺） | Router 常驻层：分派、汇总、不执行 | ❌ **你少这一层** = 计划经济委员会 |
| （缺） | 长程记忆 | 官方承认的瓶颈 |
| — | Worker 内部可再套 Subagent/Agent Team，对 Router 透明 | ✅ 你的四级在 DSH 里合法 |

**两个必须先定、当时没人拍板的地基**（10-31 21:24 之后给出建议，用户未回应）`[原话]`：

**Q-01 部委拥有什么？** 一个层级只有拥有**不可分割的东西**才成立，可选项只有四样：自己的上下文（session）/ 自己的授权（Policy/Mandate 范围）/ 自己的资源（目录、机器、token 预算）/ 自己的节拍（常驻 loop vs 一次性）。
→ **建议 A：部委不是机关，是疆域**——共享记忆域 + 预算 + 规则范围，**自己不占 session**；B（二级 Router）不要选，多一跳就多一次上下文损耗和转述失真。
> 「部委者，非会话也，乃疆域也。」部门才是机关（有 session、目录、inbox），班组是临时派的兵，不占编制。

**Q-02 "真 worker" 要不要配地址？** subagent 在 DSH 里是父进程内、有独立上下文但**没有地址**——没有 inbox、没有独立 session 目录、不能被打断、人不能直接找它、失败会牵连父会话。这与第 2 条硬约束（人人可通话）直接矛盾。
→ 分两类：**有地址的执行体**（要被找/问/中断/审计 → 必须有 session，至少到部门级）；**无地址的执行体**（一次性参谋、查资料、跑大搜索 → subagent 最合适）。
> 口诀：**要联系就别当 subagent；当 subagent 就别指望被联系。**

**条条 vs 块块**（列宁制真正的张力 = 双重领导）：工程上唯一解法是**上下文跟着"块"走，职能只当标签**。
块 = 仓库/项目/业务线 → 一个部门 session，记忆在这里沉淀；条 = 金融/开源动向 → 人设 + 提示词 + 工具集，**不是 session**。否则会产生"金融部委在 A 项目里的部门"和"A 项目里的金融职能"两份上下文，然后开始对账。`[原话]`

## 3. 当前设计 v0.1（提案，未定稿）

### 3.1 四级

| 层 | 是什么 | 拥有 | DSH 落点 | 什么时候别建 |
|---|---|---|---|---|
| 中央 / Router | 调度 + 汇总 + 对外 | 全局事件序、策略版本 | 单个常驻 session，**不配 Bash**（不执行） | 事件量小时直接用部门 |
| **部委** | **疆域**（非机关） | 共享记忆域、预算、Policy 范围 | 目录 + Policy 文件 + 账本，**无 session** | 没有跨部门共享需求时合并掉 |
| **部门** | 机关 / Worker | session、目录、inbox、Mandate | **一个 session 一个机器人** | 一次性且无需回忆时用班组 |
| **班组** | 临时执行体 | 无 | subagent | 需要被联系/中断/审计时 |

### 3.2 两条硬约束（从文章来的，别丢）

1. **Router 不执行**：它分派、汇总、对外；不配 Bash、可以用轻量模型，靠批处理扛吞吐。`[文档]`
2. **Worker 不对外**：对外只通过 Router；Worker 内部可以再套 Subagent，对 Router 透明。`[文档]`

### 3.3 汇报与异议（制度部分）

- 每部门固定出口：`00-inbox/<部门>/<日期>.md`，模板固定（frontmatter + 3–5 小节 + 来源链接 + 置信度 + 一句判断）。
- 矛盾不合并：原始报告进 `_disputes/`；**只存结论 = 稳定生产自信的废话**。
- 中央只看汇总，不看流水；聊天是异常通道（质询、开会），不是主干。

### 3.4 一条判词（用来拒绝需求）

> 部委不是会议，是疆域；部门不是功能，是机关；班组不是编制，是用完就散。
> 一个层级若说不出它**独占的东西**，就不该存在。

## 6. 断点：session 迁移（10-31 22:09 `[原话]`，答复见 §10 #4023）

用户问：「文章提到了过去 session 这种方式的缺点……我们之前不是讨论过做 session 的迁移吗」。

**先核实**：没有独立的 session 迁移方案。能对上的最近三次讨论只有——① compact 不能让它永久活着（阈值 `floor(min(W×0.8, W−O−65536))`、逐字保留 16%，结论"压缩是呼吸，不是存储"）`[源码]`；② Wake 的定位本身就是 `browse / search / resume`；③ 部门制里"session 都是孤立的"这句原话。

**文章真正说了 session 什么缺点**`[文档]`：

- 明说三条物理限制：单会话同步阻塞（工具不返回就收不到新指令）；多任务上下文互相污染；设备离线即停。体感：**人只能同时跟 3–5 个活跃 session**。
- 藏起来的狠话：8.2「以聊天窗口为中心，在一定程度上是**路径依赖**」，且「界面上看到一个会话，**底层未必只对应一个 Session**」；8.3 给组织配 agent 的本质是**划分"上下文共享 vs 隔离"的边界**。
- 隐含前提：session 把**身份**（我是谁、在跟谁说话）、**状态**（聊到哪）、**进程**（谁在跑）捆在一根绳上——**迁移难就是因为这三样捆死了，没法只搬一样**。

**所以"迁移 session"这个提法要改**：能迁移的只有**可序列化的状态**，不能迁移的是**活着的执行**（在途工具调用、子进程、锁、跑到一半的外部副作用）。正确做法是先把三样拆开，再各搬各的：

| 要搬的东西 | 拆到哪 | DSH 给的现成答案 |
|---|---|---|
| 身份 | Thread / Ticket 才是身份，session 只是当前执行体 | 文章原话「**Session 是实现细节**」`[文档]` |
| 状态 | 会话状态入库，容器无状态 | **存算分离**（该文 5.1 节） |
| 授权 | 迁移后原授权还算不算数？ | `hand-back` + `revalidation`（该文 002 授权文档）`[文档]` |
| 记忆 | 跨 session 长程记忆 | **文章自己承认的瓶颈**（8.1） |

**三档粒度**：

- **L1 冷迁移**（停—存—起）：transcript + 工具状态写库，换机恢复。安全，丢掉"在途"那一步。= 存档 → 换机 → 读档。
- **L2 热迁移**（断点续跑）：**只能在步骤边界搬**。而"步边界"就是你之前那个「输入即打断」方案里的核心——**能安全插话的地方，就是能安全交接的地方**（不是巧合）。
- **L3 任务迁移**（换执行体，不搬会话）：旧 Executor 把活**交还**、Router 重新派给新 Executor = `hand-back`；它回答了迁移里最难的问题（接手的人算不算有授权）：`revalidation`——来源还在听吗、人还在名单里吗、规则还开着吗，过了才算数。

**结论**：DSH 已经把迁移**两端**给了（状态可搬 + 授权可搬），中间缺的是"**上下文搬运格式**"：transcript 归谁、怎么压缩成状态、旧会话怎么处置。

**两个副作用（一定会撞上）**：

1. **身份分裂**：迁移后旧会话若还能被唤醒，会出现两个 owner 同时改同一个东西。判据：**迁移后同一时刻只能有一个 owner，旧会话必须降级为只读归档（append-only）**。
2. **记忆重复**：同一段对话在两份 transcript 里，将来检索召回两份。幂等规则：**以 Transcript ID 去重，不以内容去重**。

**待选方向（这是断点上的岔口）**：换机器/换客户端（L1）还是换 agent 接管（L3）？两个方向工程完全不同。

## 7. 与 DSH 现有能力的映射

> 这一节是"要落成什么样"的差距表。`[源码]` 指读过本机发行包；`[观察]` 指在当前会话/工具清单里直接看到；`[待核]` 指没核。

| 需要的能力 | DSH 现状 | 缺口/结论 |
|---|---|---|
| 一 session 一机器人 | 一个 session 就是一个上下文与执行体 `[源码]` | ✔ 天然满足 |
| 有地址的执行体（部门/成员） | 当前会话可见：`spawn_teammate` 创建**常驻成员**（`list_agents` 可见、`send_message` 可寻址）、`team_task_*` 共享任务板（状态/依赖/认领/write_scopes）`[观察]` | ✔ 部门层有了雏形；跨会话常驻未验证 `[待核]` |

| 存算分离 + 端侧 daemon | 无 `[文档]` | 远期；和 L1 迁移相关 |
| 独立 Watchdog session（监控存活与进展） | 无内建；`schedule` + 独立 session 可近似 `[假设]` | 部门多起来才需要 |
